## 3. How to run the dogfood loop

Prereqs: profiles created with a voice corpus + seed targets, and `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `APIFY_TOKEN` set.

**Daily targeting (surface candidates + draft replies):**
- UI: open `/board`, pick a profile, click **Refresh targets** (runs `refreshTargetsForProfile` for that profile).
- Or trigger the cron manually (all profiles):
  ```bash
  # local
  curl -H "authorization: Bearer local-dev-cron-secret" http://localhost:3000/api/cron/targeting
  # production
  curl -H "authorization: Bearer $CRON_SECRET" https://<your-vercel-domain>/api/cron/targeting
  ```

**Performance tracking (re-scrape metrics for recent posts):**
```bash
curl -H "authorization: Bearer $CRON_SECRET" https://<your-vercel-domain>/api/cron/tracking
# → {"ok":true,"updated":N}
```
Vercel Cron schedule (in `vercel.json`): targeting daily at 07:00 UTC, tracking every 6 h. Guardrails: targeting caps 20 tweets/handle and top-10 candidates; tracking caps 50 posts/run and skips posts older than 7 days.

**Daily human-in-the-loop flow:** `/board` → read drafted replies → Copy → reply on X → paste the tweet URL into "Mark posted" (feeds tracking). Use `/compose` for original posts. `/performance` shows likes/views once tracking runs.

**Acceptance test (per spec):** run all three accounts daily for a week; log whether the board surfaces worth-engaging accounts and whether drafts need only light edits. This feeds the 90-day re-score (currently 61/100, Marginal).

## 4. Phase 1 architecture decisions (and why)

**Goal:** replace copy/paste with direct posting, as an *opt-in layer* — v0 copy/paste stays the default.

1. **AdsPower + Playwright ONLY — no official X API.** You explicitly declined the X API write tier (~$200/mo Basic). So posting drives an AdsPower anti-detect browser (assumed already logged into X) over CDP via `playwright-core`. Zero recurring cost from our code. (`posting_jobs.method` is constrained to `'adspower'`; widening to add an `'x_api'` method later is a one-line check change + a new client.)
2. **Opt-in behind `NEXT_PUBLIC_POSTING_ENABLED`.** When unset/false, none of the posting UI renders, no posting server actions are reachable, and v0 is byte-for-byte unchanged. Per-profile config (`posting_accounts.adspower_user_id`) gates which accounts can post.
3. **Reuse v0 tracking.** On a confirmed post, `postDraft` inserts a `posts` row + marks the draft `posted` + the candidate `engaged` — so the existing performance/tracking pipeline works unchanged.
4. **Idempotency.** `postDraft` rejects already-posted drafts and a partial unique index `posting_jobs(draft_id) where status in ('running','succeeded')` blocks duplicate in-flight/successful posts at the DB. A `posting_jobs` audit row records every attempt (status, result_url, error).
5. **Security parity.** `postDraft`/`setPostingAccount` use the RLS-scoped cookie client (no service-role escalation) — same ownership model as v0; verified no IDOR.
6. **`playwright-core`** (not full `playwright`) — AdsPower supplies the browser binary, so no bundled-browser download is needed.

`src/lib/posting/x-poster.ts` (`postTweetViaAdsPower`) is the only **live-only / untested** module — it cannot run without an AdsPower install + a logged-in X session.

## 5. Security hardening applied (commit `2f534ae`)

A review caught and fixed: (1) **IDOR** — `refreshTargets` now verifies profile ownership (RLS read) before invoking the service-role orchestrator; (2) **cron bypass** — both cron routes reject when `CRON_SECRET` is unset (no more `Bearer undefined` pass); (3) **open redirect** — `/auth/callback` restricts `next` to same-origin paths; (4) **duplicate detection** — `markPosted` uses Postgres code `23505` not message text; (5) middleware matcher exempts only `api/cron/`, not the whole `api` namespace.
